# Правила работы с Figma

## Назначение

Этот документ определяет, как макеты Figma должны интерпретироваться и реализовываться в этом проекте.

Figma передаёт дизайн-замысел и контекст конкретной страницы.

Репозиторий определяет правила реализации.

При реализации макета из Figma не воспроизводи фрейм как изолированную визуальную копию. Собирай интерфейс с использованием существующей дизайн-системы, архитектуры, токенов, компонентов и layout-правил проекта.

---

## Источники истины

Используй следующий приоритет источников:

1. Архитектура проекта и документированные правила реализации
2. Существующие компоненты и паттерны дизайн-системы
3. Семантические токены
4. Foundation-токены
5. Контекст макета из Figma

Figma является источником истины для:

- структуры страницы;
- контента;
- композиции компонентов;
- визуальной иерархии;
- задуманного layout;
- адаптивного поведения, если оно явно представлено в макете;
- ассетов и иллюстраций;
- состояний и вариантов компонентов, показанных в макете.

Репозиторий является источником истины для:

- архитектуры реализации;
- API компонентов;
- названий токенов;
- иерархии токенов;
- переиспользуемых layout-паттернов;
- responsive-правил;
- соглашений по коду;
- существующего поведения дизайн-системы.

---

## Работа через Figma MCP

Когда предоставлена ссылка на Figma или конкретный объект в Figma:

1. Используй Figma MCP для изучения указанного фрейма или объекта.
2. Получи и изучи design context до начала реализации.
3. Определи структуру страницы и переиспользуемые UI-паттерны.
4. Сопоставь элементы макета с существующей дизайн-системой в репозитории.
5. По возможности используй существующие компоненты, семантические токены и layout-паттерны.
6. Реализуй дизайн в соответствии с правилами репозитория, а не путём механического переноса значений из Figma в код.

Не рассматривай автоматически сгенерированный из Figma код как production-код.

---

## Сопоставление токенов

Не переноси raw-значения из Figma непосредственно в код автоматически.

Например, если в Figma указано:

    gap: 40px

сначала определи, соответствует ли это значение существующему семантическому токену.

Предпочтительно:

    значение Figma
        ↓
    semantic token
        ↓
    foundation token

Избегай:

    значение Figma
        ↓
    hardcoded CSS value

Используй семантический токен всегда, когда подходящий семантический токен существует.

Не обходи семантический слой, используя соответствующее значение Foundation напрямую.

---

## Отсутствующие токены

Если необходимое для реализации значение из Figma отсутствует в существующей дизайн-системе:

- не создавай новый токен автоматически;
- не добавляй значение в код как hardcoded value без предупреждения;
- не изменяй существующий токен только ради совпадения с конкретным фреймом.

Сначала сообщи о расхождении.

Укажи:

- значение в Figma;
- где оно используется;
- какой существующий токен или правило наиболее близки;
- выглядит ли расхождение намеренным или случайным;
- какое изменение дизайн-системы потребуется для его поддержки.

Дождись решения перед изменением дизайн-системы.

---

## Компоненты

Перед созданием нового компонента:

1. Проверь, может ли существующий компонент дизайн-системы реализовать этот интерфейс.
2. Проверь, достаточно ли существующего варианта компонента или композиции существующих компонентов.
3. Проверь, соответствует ли интерфейс существующему переиспользуемому паттерну.

Не создавай page-specific копии существующих компонентов дизайн-системы.

Не изменяй shared-компонент только ради воспроизведения одного экземпляра из Figma, если такое изменение повлияет на его системное поведение.

Если дизайн требует поведения, которого нет в текущем API компонента, сначала сообщи о расхождении.

---

## Layout

Используй документированную layout-систему проекта и существующие responsive modes.

Не создавай новые глобальные breakpoints на основании ширины отдельных Figma-фреймов.

Текущие layout modes:

- narrow: 320–640px
- medium: 641–1279px
- wide: 1280px и более

Ширина Figma-фрейма является примером состояния дизайна внутри responsive mode, а не обязательно CSS breakpoint.

Используй существующие layout-паттерны, если они соответствуют макету.

Например, повторяющиеся двухколоночные композиции должны использовать существующий переиспользуемый паттерн SideBySide, а не реализовывать двухколоночное поведение независимо для каждой секции.

---

## Responsive-поведение

Не предполагается, что в Figma представлены все возможные ширины viewport.

Используй доступные Figma-фреймы для определения дизайн-замысла, а между этими состояниями применяй responsive-правила проекта.

Не создавай произвольное breakpoint-specific поведение, если соответствующее поведение уже определено дизайн-системой для данного компонента или паттерна.

Если responsive-поведение невозможно однозначно определить ни из Figma, ни из существующей системы, сообщи о неопределённости вместо скрытого предположения.

---

## Визуальное соответствие

Реализация должна сохранять задуманный визуальный результат макета Figma и одновременно соответствовать дизайн-системе.

Визуальное соответствие не является основанием для:

- дублирования компонентов;
- обхода семантических токенов;
- добавления произвольных hardcoded values;
- создания ненужного одноразового CSS;
- нарушения существующего responsive-поведения;
- изменения глобальных правил дизайн-системы ради одной страницы.

Если Figma и дизайн-система противоречат друг другу, сообщи о конфликте вместо того, чтобы скрывать его в реализации.

---

## Перед реализацией

Перед существенной работой на основе Figma сначала изучи:

- указанный Figma-фрейм;
- соответствующие токены дизайн-системы;
- существующие компоненты;
- существующие layout-паттерны;
- документацию проекта, относящуюся к реализуемому интерфейсу.

До написания кода выяви существенные расхождения между макетом Figma и существующей системой.

Незначительные детали реализации, уже определённые правилами и соглашениями проекта, не требуют дополнительного согласования.

---

## Цель

Цель — не:

    Figma → визуальная копия

Цель:

    дизайн-замысел Figma
            +
    дизайн-система проекта
            +
    архитектура проекта
            ↓
    поддерживаемая production-реализация

 ## Перенос текста и пунктуации

При переносе текста из Figma необходимо сохранять текст как цельную языковую строку.

- Знаки препинания не отделяются пробелом или отдельным переносом от предшествующего слова.
- Точка, запятая, двоеточие, точка с запятой, закрывающая скобка и другие знаки препинания не должны становиться отдельными текстовыми узлами только ради воспроизведения переноса строки из Figma.
- Переносы строк из конкретной ширины Figma-фрейма не считаются частью текстового контента, если они не заданы явно как смысловые.
- Естественный перенос текста должен выполнять браузер в зависимости от ширины контейнера.
- Не использовать `<br>` для визуального воспроизведения переносов из Figma без явного требования дизайна.
- При необходимости управлять неразрывностью текста использовать типографически корректные решения, не изменяя сам текст без необходимости.
