# Design System Principles

Этот документ описывает принципы, на которых построена дизайн-система. Они важнее конкретных токенов, компонентов или паттернов, потому что помогают принимать новые решения последовательно и без противоречий.

---

## 1. Single Responsibility

Каждая сущность имеет одну чёткую область ответственности.

- Primitives хранят физические значения.
- Semantic Tokens описывают смысл.
- Layout Patterns управляют расположением элементов.
- Components собирают интерфейс из паттернов и токенов.
- Pages собираются из компонентов.

Ни один уровень не должен выполнять работу другого.

---

## 2. Single Owner

У каждого решения существует один владелец.

Если за расстояние отвечает Layout Pattern, компонент не должен задавать это расстояние повторно.

Если за типографику отвечает Semantic Token, компонент не должен хранить размеры шрифта.

Если за внутренние отступы отвечает Surface, Section не должна пытаться ими управлять.

Дублирование ответственности запрещено.

---

## 3. Semantics over Values

Компоненты работают не с физическими значениями, а со смыслом.

Правильно:

- `text/body`
- `spacing/section/outer`
- `color/text/primary`

Неправильно:

- `16px`
- `#111111`
- `40px`

Физические значения принадлежат только фундаментальному уровню системы.

---

## 4. Composition over Specialization

Сложные интерфейсы собираются из простых универсальных паттернов.

Вместо создания специализированных компонентов предпочтение отдаётся композиции существующих решений.

Например:

- Section использует SideBySide.
- Section может использовать Grid.
- Section может использовать Stack.

Паттерны не знают друг о друге и не зависят от конкретных страниц.

---

## 5. Patterns describe behavior

Layout Patterns описывают поведение, а не внешний вид.

Они определяют:

- правила раскладки;
- адаптивность;
- направление потока;
- порядок элементов;
- допустимые параметры.

Они не определяют:

- цвета;
- типографику;
- содержимое;
- визуальный стиль компонентов.

---

## 6. Prefer reusable abstractions

Новые сущности появляются только тогда, когда возникает повторяющийся паттерн.

Если правило используется один раз, оно остаётся локальным.

Если правило начинает регулярно повторяться, оно становится частью дизайн-системы.

Система растёт только под влиянием реальных потребностей.

---

## 7. Keep the hierarchy clean

Архитектура системы должна оставаться простой и предсказуемой.

```
Primitives
    ↓
Semantic Tokens
    ↓
Layout Patterns
    ↓
Components
    ↓
Templates / Pages
```

Каждый уровень знает только то, что относится к его ответственности.

---

## 8. Document decisions

Каждое архитектурное решение должно быть объяснено.

Важно фиксировать не только принятое решение, но и причину его появления.

Документация должна отвечать не только на вопрос «как устроено», но и на вопрос «почему именно так».

---

## Goal

Цель этой дизайн-системы — не максимальное количество токенов или компонентов, а минимальная сложность при максимальной предсказуемости.

Любое новое решение должно:

- иметь одного владельца;
- не дублировать существующую ответственность;
- быть переиспользуемым;
- укладываться в общую архитектуру системы.
